# 项目代码知识库设计方案

## 1. 目标与边界

本知识库面向参与本仓库开发的 AI，帮助其在处理需求时快速回答四个问题：

1. 应该先查看哪个模块？
2. 该模块的需求、职责和实现逻辑是什么？
3. 修改会影响哪些接口、模块和测试？
4. 修改完成后应如何验证？

知识库不替代源码、测试、接口定义和 CodeGraph：

- 源码、测试和 `contracts/` 是事实来源。
- `.codegraph/` 负责函数、类型、调用链等代码证据。
- `docs/knowledge/` 记录模块语义、业务意图、职责边界和任务路由。

首版不为每个文件、类或函数重复编写文档，也不手工维护完整调用图。

## 2. 设计原则

1. **代码优先**：文档必须链接到具体源码、测试或接口，不能脱离代码独立存在。
2. **按职责建模**：以可独立理解、修改和验证的模块为单位，不机械地按文件夹建文档。
3. **需求与实现分离**：每个模块分别说明“应该做什么”和“当前如何实现”。
4. **关系可追溯**：模块关系必须标注类型和证据路径。
5. **小而可维护**：先覆盖顶层模块和高频开发路径，复杂子模块按需拆分。
6. **自动事实、人工语义**：文件、符号和调用关系可自动提取；职责、边界和设计决策由文档维护。

## 5. 模块文档模板

每个模块文档使用相同结构，确保 AI 能按固定顺序获取信息：

```markdown
---
id: module.example
type: module
status: active
source_paths:
  - path/to/source
related_modules:
  - module.other
last_verified: YYYY-MM-DD
---

# 模块名称

## 1. 模块定位

说明模块为什么存在，以及它在整个系统中的位置。

## 2. 业务需求

说明该模块应该完成的业务目标、用户场景和规则。

## 3. 职责边界

### 负责

- 明确职责。

### 不负责

- 明确由其他模块承担的职责。

## 4. 核心实现逻辑

用流程说明当前实现：

请求进入 -> 参数校验 -> 业务处理 -> 调用依赖 -> 输出结果

## 5. 关键源码和入口

- 源码路径。
- 入口函数、类或路由。
- 关键数据结构或接口。

## 6. 输入、输出和状态

说明请求、响应、事件、状态变化和持久化数据。

## 7. 依赖和影响

说明依赖谁、被谁调用，以及改动可能影响的模块。

## 8. 验证方式

列出相关测试、命令和手工验收场景。

## 9. 已知限制

记录未覆盖场景、技术债和临时约束。
```

## 6. 模块关系和元数据

`_meta/modules.yaml` 提供模块的稳定身份、别名和文档入口：

```yaml
- id: agent.streaming
  name: Agent 流式编排
  aliases:
    - 流式响应
    - streaming
    - SSE
  source_paths:
    - agent/src/scyg_agent/transport
    - agent/src/scyg_agent/runtimes
  document: 03-modules/agent/overview.md
  status: active
  keywords:
    - 对话
    - 工具调用
    - 流式输出
```

`_meta/relations.yaml` 记录模块级关系，每条关系都保留代码证据：

```yaml
- from: frontend.chat
  to: agent.streaming
  type: consumes
  description: 前端消费 Agent 流式事件。
  evidence:
    - frontend/src/request/
    - frontend/src/services/
  confidence: high

- from: agent.streaming
  to: contracts.agent
  type: produces
  description: Agent 输出由协议定义的流式事件。
  evidence:
    - agent/src/scyg_agent/transport/
    - contracts/proto/scyg/agent/
  confidence: high
```

关系类型统一使用：

| 类型 | 含义 |
| --- | --- |
| `calls` | 代码调用。 |
| `consumes` | 消费接口、事件或数据。 |
| `produces` | 产生接口、事件或数据。 |
| `reads` / `writes` | 读取或写入数据。 |
| `implements` | 实现某个契约。 |
| `tested_by` | 被测试覆盖。 |
| `configured_by` | 行为由配置控制。 |
| `deployed_with` | 需要共同部署或启动。 |

## 7. AI 检索流程

AI 处理任务时遵循以下路径：

```text
用户任务
  -> 00-index.md：按任务类型和关键词定位
  -> modules.yaml：查找模块 ID、别名和源码入口
  -> 模块文档：理解需求、职责、实现和边界
  -> relations.yaml：确认上下游影响范围
  -> CodeGraph：定位函数、类型和调用链
  -> interfaces 与 verification：确认契约和验证方式
  -> 修改代码并执行相关验证
```

例如“修改聊天流式响应格式”应定位到：

```text
frontend.chat
  -> agent.streaming
  -> contracts.agent
  -> 前端流式解析测试
  -> Agent 传输层和契约测试
```

## 8. 现有文档的迁移策略

现有文档不立即删除或复制，先建立来源映射并逐步收敛：

| 现有位置 | 知识库目标位置 |
| --- | --- |
| `docs/agent-service-development.md` | `03-modules/agent/overview.md` |
| `docs/agent-streaming-architecture.md` | `02-domain/workflows/agent-streaming.md` |
| `docs/runbooks/` | `07-operations/runbooks/` |
| `backend/docs/architecture/` | `01-system/` 或 `03-modules/backend/` |
| `backend/docs/guides/` | `05-playbooks/` 或 `07-operations/` |

在完成内容合并和链接检查前，旧文档继续保留。`_meta/sources.yaml` 应标记每篇知识库文档的原始来源和关键源码路径。

## 9. 分阶段实施

### 第一阶段：建立最小可用导航

1. 创建 `docs/knowledge/` 骨架。
2. 编写 `00-index.md`、`01-system/overview.md` 和 `repository-map.md`。
3. 为 `agent`、`backend`、`frontend`、`contracts` 分别编写一篇 `overview.md`。
4. 建立 `modules.yaml` 和初始 `relations.yaml`。
5. 整理构建和测试命令到 `06-verification/commands.md`。

### 第二阶段：补充高频模块和流程

1. 完成 Agent 分层文档、Backend Content 模块、Frontend 请求和视图模块、协议模块。
2. 补充文章发布、聊天和流式响应等端到端流程。
3. 建立接口、错误模型和兼容性文档。

### 第三阶段：自动化和一致性检查

1. 通过 CodeGraph 或脚本生成文件、符号和关系索引。
2. 检查文档中的源码路径、模块 ID 和链接是否有效。
3. 在模块职责、接口、运行命令或验证方式变化时同步更新对应文档。

## 10. 首版边界与验收

首版覆盖系统总览、四个顶层模块、主要模块关系、契约入口和验证入口。首版暂不建设向量数据库、完整知识图谱服务、全部函数文档或完整调用图副本。

首版通过的标准是：给定一项开发任务，AI 能从知识库中确定目标模块、理解其需求和实现逻辑、找出影响范围、定位源码入口，并得到明确的验证方式。
