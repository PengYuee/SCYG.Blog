# 业务模块

本目录按用户要完成的业务组织正式说明，不按进程或源码目录拆分。一个模块可以跨浏览器、Blog 和 Agent；读者应能在一份模块文档中读完正常流程、约束、状态变化、关键失败结果及数据归属，再沿实现与测试入口复核。

## 按业务阅读

| 模块 | 解决的问题 | 直接协作 |
| --- | --- | --- |
| [登录与会话](authentication.md) | 怎样登录、恢复与退出，浏览器门禁和真正服务端授权各保证什么 | 前端登录/请求/路由，Blog identity 与认证适配 |
| [文章管理](articles.md) | 公开与管理读取、草稿编辑、发布、归档、删除、版本冲突和写事务 | Blog article/application，前端编辑器，分类与正文图片 |
| [分类与标签](taxonomy.md) | 分类标签的管理、公开投影、引用删除约束和分类配图 | Blog taxonomy 与文章引用，前端分类管理和卡片 |
| [文章图片](article-images.md) | 上传文件、正文绑定、媒体可见性、取消及后台清理为何不同 | 前端图片跟踪，Blog image/application，Blob 与清理 worker |
| [AI 任务与作者辅助](ai-assistance.md) | 四能力、同 Run 人工交互、结果、未知操作、恢复和取消 | 前端工作台，Blog HTTP/SSE，Agent 控制面、Worker 与执行图 |
| [公共 AI 搜索](public-ai-search.md) | 访客身份、公开内容、公共接纳与日额度及故障差异 | 前端匿名分区，Blog 凭证/频率/SSE，Agent/Redis/公开内容读取 |

首次理解作者业务时，先读登录与会话，再按文章、分类和图片的协作关系阅读。理解 AI 时，先读共同任务及作者流程，再读公共搜索差异；公共页不重新定义另一套 Run 状态或幂等规则。

## 与其他资料的分工

- [项目架构](../architecture.md)维护整体技术关系与资料导航，不展开每个模块的完整业务流程。
- [服务文档](../README.md)维护进程职责、配置、装配、部署和技术验证。服务中的模块映射应链接本目录，不另抄一份状态和失败规则。
- [OpenAPI](../../backend/api/openapi.yaml)与[共享 Proto](../../contracts/proto/)维护传输字段、路径和协议类型；模块只解释业务含义，不复制字段全集。
- 需求与设计描述目标，模块描述已实现行为；现有能力不足时应明确写边界，不能为文档看起来完整而虚构功能或顺手改变实现。
- Wiki 提炼跨模块关系、决策和导航，不代替本目录的正式业务说明。原始日志、授权过程、审查输出与临时环境保留任务材料，不写成长期业务约定。

## 如何维护和验证

修改业务时，从对应模块中的源码、合同和测试入口复核；涉及其他模块的事实使用链接，不重新定义对方规则。共享行为只在最合适的模块维护，例如 Run 生命周期由 AI 任务说明负责、匿名用途与公共额度由公共搜索说明负责。

各页列出的测试是维护和验收入口，不表示一次文档整理运行过全部用例。配置检查、服务 readiness、行为测试和真实业务回执各有范围；是否在某个环境通过，应核对该版本的执行结果，不能只看本目录或某个助手的完成报告。
