# 通用文档编写方法论

文档的作用，是帮助特定读者完成理解、操作或决策。好的文档应当事实准确、路径短、边界清楚、结果可验证，并且知道由谁、在何处维护。

日常写作执行六步方法，并在完整起草前通过方向确认门禁。交付前完成检查清单，文档类型、图表和案例等扩展内容按需查阅。

## 一、六步核心方法

### 1. 定目标

先回答：

> 谁会读，读完要完成什么？

确认读者的当前状态、目标和下一步行动。删除与这个结果无关的内容，不从源码目录、已有材料或固定模板开始堆砌章节。

### 2. 查事实

根据文档类型查找当前权威来源：

- 行为和机制：源码、协议、测试和运行结果；
- 配置和命令：配置文件、构建文件、脚本和项目约定；
- API 和数据格式：接口定义、Schema、Proto 和错误码；
- 设计和决策：现状、约束、候选方案和决策记录；
- 故障和恢复：真实日志、时间线、修复和验证结果。

历史文档、注释和目录结构只能帮助定位。区分当前事实、规范要求和推断；无法确认的内容不写成确定结论，样例和环境现象应标明适用范围。

### 3. 划边界并确定事实归属

确定当前文档负责回答什么，并在直接边界停止。每项事实还应判断属于哪个层级：

- 项目或体系的公共规则；
- 当前对象的特有行为；
- 下层业务模块的规则；
- 其他系统的内部实现。

跨系统关系说明调用方、交互方式和目标选择即可，不展开下游内部处理。公共规则集中维护，当前对象文档重点说明自身差异；同一事实只保留一个权威位置，其他地方引用，不复制易变化的细节。

### 4. 按需横向比较

出现公共协议、公共基类、重复回调、通用基础设施，或准备写出一段可以原样复制到多个同类文档的内容时，比较相关对象的实现：

- 入口是否相同；
- 行为是否相同；
- 状态、门禁和失败结果有何差异；
- 哪部分应集中维护，哪部分应留在当前对象文档。

相同入口不代表相同行为。例如多个服务都接收冻结协议，但退出前等待的负载可能不同。横向比较只在这些信号出现时触发，不为普通局部事实扫描整个项目。

### 方向确认门禁

完成前四步后，AI 在编写完整正文前先向用户提交一份简短的方向说明：

- 目标读者和阅读结果；
- 已确认的权威来源；
- 文档范围和事实归属；
- 公共规则与当前对象的主要差异；
- 拟采用的正文结构；
- 尚未确认的事实或需要用户决定的事项。

提交后必须暂停，等待用户确认方向。用户提出修正时，先更新方向说明，不直接开始完整写作；用户确认后再进入第五步。

局部错字、失效链接、明确的单点事实修正不需要方向确认。用户已经给出明确范围和结构，或明确要求直接编写时，也可以跳过该门禁。

### 5. 写主路径和局部差异

先写最短但完整的正文，顺序通常是：

```text
结论或目标 → 最短路径 → 前置条件 → 关键分支和失败 → 原理与参考
```

机制说明优先回答：

- 谁在什么条件下执行；
- 按什么顺序执行；
- 成功后发生什么；
- 失败后如何处理；
- 是否等待、重试或回退；
- 最终进入什么状态。

公共背景只保留理解当前对象所需的最少内容，重点展开当前对象与公共规则不同的行为。直接陈述事实，不用“下面说明”“需要特别强调”“下图用于概括”等提示语代替内容。

### 6. 做验证

验证文档承诺的内容，而不只检查文字是否通顺：

- 命令和示例能够在声明的环境中执行；
- 配置、接口、路径和术语与当前实现一致；
- 成功标准和主要失败结果明确；
- 公共规则和当前对象差异没有混淆；
- 相对链接和交叉引用有效；
- 图表可以渲染并与正文一致；
- 易变事实有明确的维护位置。

## 二、六条硬规则

1. **结论和最短路径优先**：背景和原理放在必要信息之后。
2. **只写经过确认的事实**：推断和样例必须标明范围。
3. **先归类，再展开**：公共规则写一次，当前文档重点写局部差异。
4. **一项事实只维护一个权威位置**：其他位置使用引用或链接。
5. **正文独立表达关键内容**：删除图表后，主要事实、条件和结果仍然完整。
6. **辅助形式必须降低理解成本**：图表、表格、示例和模板不是必选项。

KISS 不等于一味缩短。必要的前置条件、限制、风险、失败结果和验证方式不能为了简短而删除。

## 三、选择合适的文档类型

不同文档解决不同问题，不应强行使用同一模板。

| 类型 | 主要问题 |
| --- | --- |
| 概览 | 它是什么、解决什么问题、与谁交互 |
| 教程 | 如何从零完成第一次成功 |
| 操作手册 | 如何重复执行，失败时如何处理 |
| 参考文档 | 字段、参数、接口和错误码分别是什么 |
| 设计或决策文档 | 为什么选择当前方案，约束和代价是什么 |
| 故障手册或复盘 | 如何识别、恢复、验证并避免再次发生 |

同一主题可以有多种文档。例如教程负责首次成功，参考文档负责完整参数；不要把两者混成一篇既长又难查的文档。

## 四、选择合适的表达形式

| 内容 | 推荐形式 |
| --- | --- |
| 完整规则或结论 | 段落 |
| 有严格顺序的动作 | 编号列表 |
| 并列事实 | 项目列表 |
| 需要横向比较的信息 | 表格 |
| 命令、配置和接口示例 | 代码块 |
| 系统之间的关系 | 架构图 |
| 判断和分支 | 流程图 |
| 多方动态交互 | 时序图 |
| 单一对象的状态迁移 | 状态图 |

正文先说明事实，再按需添加图表。图表只回答一个主要问题，不展开无关层级；图下不逐项复述节点和连线。

完成图表后执行删图检查：

> 删除所有图表后，读者是否仍能理解关键行为？

如果不能，先补正文，而不是继续向图中增加节点。

## 五、范围和维护原则

### 正面表达边界

优先写当前对象实际负责什么。只有存在反复误解、所有权争议或实际风险时，才补充“不负责什么”。

不推荐：

```text
下面说明 Gate 的直接边界。Redis 不由客户端或业务处理器直接访问。
```

推荐：

```text
客户端通过 Gate 建立 TCP 连接。Gate 通过异步请求队列访问 Redis。
```

### 分离不同层级的内容

项目规则、运行单元、业务模块和具体操作通常由不同文档维护。例如：

- 项目文档维护公共环境和总体约定；
- 服务或应用文档维护运行职责、公共机制和直接交互；
- 业务模块文档维护业务规则、数据和状态；
- 操作手册维护可执行步骤、结果和恢复方法。

没有对应文档时，也不要把不属于当前范围的内容临时塞入其中。

### 公共规则与局部差异

相同协议、接口或回调只说明入口相同，不能据此认定处理行为相同。公共文档说明共享语义；对象文档保留理解所需的最少背景，并重点说明本对象的状态、门禁、失败结果和其他差异。

如果暂时没有公共文档，不要立即创建抽象层，也不要把完整公共规则复制到每份对象文档。先简要交代背景并记录局部差异，等公共内容确实需要独立维护时再集中沉淀。

### 删除过期内容

实现、命令或配置完成切换后，删除已失效的说明。除非确实需要支持多个版本，否则不要同时保留两套相互冲突的路径。

## 六、常见反模式

- **源码翻译**：逐层记录函数调用，而不提炼条件、顺序和结果；
- **文件清单**：列出大量路径，却没有说明修改、运行或排障入口；
- **图表代替正文**：关键状态和失败分支只能从图中推断；
- **范围失控**：把项目、服务、业务、接口和操作内容全部塞进一篇文档；
- **抽象评价**：使用“功能完善”“处理可靠”等无法验证的描述；
- **无证据推断**：根据命名、注释、历史文档或架构常识补全行为；
- **重复强调**：反复解释章节目的、边界或图表作用，而不直接陈述事实；
- **重复维护**：在概述、表格、图表、操作说明或多个同类文档中复制同一易变信息；
- **只做纵向分析**：只追踪当前对象的调用链，不比较公共入口在同类对象中的实现差异；
- **相同入口等于相同行为**：看到相同协议或回调，就直接套用统一的状态、门禁和失败结论。

## 七、简短案例

### 架构概览只写外部关系

```text
客户端通过 Gate 建立 TCP 连接。Gate 主动连接 Center 完成注册和服务发现，并按发现结果连接内部服务。Gate 通过异步请求队列访问 Redis。
```

进程内用户对象和索引属于连接生命周期，不需要为了说明“架构图没有画什么”而放入架构概览。

### 公共协议只写一次，服务差异分别说明

Center 的退出、冻结和 Ping 属于公共控制协议，但服务处理并不完全相同。例如 Gate 等待用户排空，Scene 等待角色排空，Social 的延迟检查直接退出。公共说明维护协议语义，各服务文档只展开自己的退出门禁和重载行为。

### 正文独立说明流程

对于启动、登录、消息分发、配置重载或退出流程，正文应写清顺序、门禁、回退和失败结果；流程图随后提供整体路径。不能让读者只能从图中判断“什么时候进入运行”“失败后返回什么”或“哪些队列必须排空”。

### 用运行规则代替调用链

不写：

```text
Main 调用 Init，Init 调用 Config，Config 调用 Register。
```

改写为：

```text
启动时先加载配置和公共资源，再绑定网络并完成注册；必要服务装配失败时，应用不进入稳定运行状态。
```

## 八、交付检查清单

- [ ] 目标读者和阅读结果明确；
- [ ] 关键结论来自当前权威来源；
- [ ] 当前事实、规范要求和推断已经区分；
- [ ] 每项事实已归入公共规则、当前对象、下层模块或其他系统；
- [ ] 新建或大幅重写文档前，方向说明已经得到用户确认；
- [ ] 遇到公共协议、基类或重复回调时，已比较相关对象的共同点和差异；
- [ ] 可以原样复制到多个同类文档的内容已经集中维护或压缩；
- [ ] 公共规则和易变事实各自只有一个主要维护位置；
- [ ] 文档范围清楚，没有展开其他对象的内部实现；
- [ ] 主路径、前置条件、关键分支和失败结果完整；
- [ ] 没有重复、源码翻译、抽象评价和多余提示语；
- [ ] 图表、表格和示例确实降低了理解成本；
- [ ] 命令、示例、链接和图表已经验证；
- [ ] 旧实现、旧命令和失效引用已经删除。

## 结语

> **定目标，查事实，划边界与归属，横向比较；确认方向后，写主路径并做验证。**

读者只应在需要时承担相应的理解成本。核心方法保持简单，具体类型、案例和检查按需展开。
