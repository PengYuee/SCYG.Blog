# 用户认证模块实施计划

## 1. 目标

为 `backend/` 增加最小可运行的用户认证能力：

- 增加 `users` 表；
- migration 幂等写入一个默认用户 `admin`；
- 默认密码为 `666666`，数据库只保存 bcrypt hash；
- 提供用户名密码登录接口；
- 签发和验证 JWT Bearer Token；
- 将已认证用户注入请求上下文；
- 使用认证身份保护管理端内容操作；
- 保持公开内容读取接口无需登录。

不实现注册、刷新 Token、注销、密码修改、用户管理、多角色和权限管理。

## 2. 当前事实与约束

- `backend/` 是独立 Go module，运行时依赖由 `internal/bootstrap/` 手工装配。
- REST 源契约是 `backend/api/openapi.yaml`；生成 bindings 和内嵌文档由 Task 命令维护。
- 数据库结构通过版本化 SQL migration 管理，运行时只检查 migration 版本，不自动执行 migration。
- 当前 migration 版本为 `3`，新增用户表后版本为 `4`。
- GORM 只在 feature Repository 内访问所属表；不使用 `AutoMigrate`、`gorm.Model` 或 `gorm.DeletedAt`。
- 当前生产授权默认为 `DenyAll`；当前作者身份由 `CurrentAuthorProvider` 提供，图片所有者 ID 要求 32 位小写十六进制。
- 当前 OpenAPI 未声明安全方案，管理端写入由业务授权器控制。
- 当前 Go module 没有直接 JWT 依赖；密码校验需要将 `golang.org/x/crypto` 作为直接依赖，JWT 使用 `github.com/golang-jwt/jwt/v5`。

## 4. 数据库设计

### 4.1 `users` 表

使用稳定的 32 位小写十六进制用户 ID，以兼容现有 `content.AuthorID` 和图片 `owner_id` 约定：

```sql
CREATE TABLE users (
  id varchar(32) PRIMARY KEY
    CONSTRAINT users_id_check CHECK (id ~ '^[0-9a-f]{32}$'),
  username varchar(64) NOT NULL,
  password_hash varchar(255) NOT NULL,
  is_active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL,
  updated_at timestamptz NULL,
  CONSTRAINT users_username_check CHECK (length(username) BETWEEN 1 AND 64),
  CONSTRAINT users_password_hash_check CHECK (length(password_hash) > 0)
);
CREATE UNIQUE INDEX users_username_idx ON users (username);
```

默认用户固定为：

```text
id:       00000000000000000000000000000001
username: admin
password: 666666
```

Migration 中保存 `666666` 的 bcrypt hash，不保存明文密码。

### 4.2 默认用户写入

`000004_users.up.sql` 创建表并执行幂等插入：

```sql
INSERT INTO users (id, username, password_hash, is_active, created_at)
VALUES (..., 'admin', '<bcrypt hash>', true, CURRENT_TIMESTAMP)
ON CONFLICT (username) DO NOTHING;
```

冲突时不更新密码，避免重复 migration 覆盖管理员后续修改的数据。

`000004_users.down.sql` 删除 `users` 表。同步更新 `migrations.CurrentVersion` 为 `4`，并新增 migration source contract 测试。

## 5. 配置设计

新增运行时配置：

```yaml
auth:
  jwt_secret: "replace-with-a-long-random-secret"
  jwt_issuer: "scyg-blog"
  access_token_ttl: 2h
```

配置职责：

- 数据库中的 `users` 记录负责账号和密码；
- 配置负责 JWT 签发参数；
- `jwt_secret` 不写入日志、错误响应或配置摘要；
- `jwt_secret` 非空，生产环境要求至少 32 字节；
- `jwt_issuer` 非空；
- `access_token_ttl` 大于零；
- 配置错误在启动阶段失败。

更新 `config.example.yaml`、运行时配置类型、Viper 原始结构、环境变量绑定和校验测试。

## 6. 身份与登录流程

### 6.1 登录

新增：

```http
POST /api/v1/auth/login
```

请求：

```json
{"username":"admin","password":"666666"}
```

成功响应：

```json
{
  "access_token": "<JWT>",
  "token_type": "Bearer",
  "expires_in": 7200
}
```

登录用例顺序：

```text
HTTP DTO
  -> 输入校验
  -> 查询活动用户
  -> bcrypt 校验密码
  -> 由 JWT signer 签发 Token
  -> 返回登录结果
```

用户不存在、密码错误和禁用用户统一返回 `401 Unauthorized`，不泄露账号存在性。

### 6.2 JWT

使用 HS256。Claims 至少包括：

```json
{
  "iss": "scyg-blog",
  "sub": "00000000000000000000000000000001",
  "iat": 0,
  "exp": 0
}
```

验证要求：

- 只接受配置的 HS256 算法；
- 校验签名、issuer、subject、issued-at 和 expiry；
- subject 必须是合法用户 ID；
- Middleware 验证 Token 后查询当前活动用户，确保被禁用用户的旧 Token 不再有效；
- 验证失败统一返回 `401`。

### 6.3 当前用户

请求上下文保存：

```go
type Principal struct {
    UserID   string
    Username string
}
```

已认证的用户 ID转换为现有 `content.AuthorID`，由当前作者 Provider 提供给文章图片和内容写入路径。

## 7. REST 与授权

### 7.1 公开路径

以下路径继续公开：

- `POST /api/v1/auth/login`；
- 公开文章读取；
- 公开文章类型和标签读取；
- 已提交图片媒体读取；
- `/live`、`/ready`、文档和 OpenAPI 资源。

### 7.2 受保护路径

以下操作要求有效 JWT：

- `/api/v1/manage/**`；
- `POST /api/v1/manage/article-images`；
- `DELETE /api/v1/article-images/{image_id}`。

认证失败由 Middleware 返回 `401`。bootstrap 注入基于 Principal 的 Authorizer 和 CurrentAuthorProvider；第一版单用户模型下，认证用户允许现有管理操作并作为当前作者。未来角色和权限加入后，再替换授权决策实现，不改变登录和当前身份边界。

### 7.3 OpenAPI

在 `api/openapi.yaml` 中：

- 增加 `bearerAuth` security scheme；
- 登录接口声明 `security: []`；
- 管理接口声明 `security: [{bearerAuth: []}]`；
- 增加 LoginRequest、LoginResponse 和 Unauthorized 定义；
- 同步 401 响应、错误格式和生成 bindings；
- 执行 `task api:generate` 与 `task api:docs:sync`。

## 8. 实施阶段

### 阶段一：用户表和 migration

交付：

- `000004_users.up.sql`；
- `000004_users.down.sql`；
- 默认 `admin` 账号 bcrypt hash；
- `CurrentVersion = 4`；
- migration source contract 测试。

验收：

- `users` 表约束和唯一索引符合设计；
- 默认账号只出现一次；
- bcrypt hash 可以验证密码 `666666`；
- migration 可执行 `up -> down -> up`；
- 不修改现有内容表和业务数据。

### 阶段二：identity/user

交付：

- User 领域类型；
- User Record、Mapper 和 Repository；
- 活动用户按用户名查询；
- bcrypt 密码校验；
- 用户错误转换；
- Repository 单元测试和真实 PostgreSQL integration 测试。

验收：

- 只查询 `users` 表；
- 查询绑定 context；
- 禁用用户不可作为登录用户；
- 数据库错误不泄露 DSN、密码 hash 或 SQL 敏感值。

### 阶段三：登录用例和 JWT

交付：

- 登录 application；
- JWT signer/verifier；
- Principal 和 context 读写；
- `golang-jwt/jwt/v5` 直接依赖；
- `golang.org/x/crypto` 直接依赖；
- 单元测试。

验收：

- `admin/666666` 能签发 JWT；
- 错误用户名、错误密码和禁用用户返回同一认证失败；
- Token Claims 正确；
- 错误签名、算法、issuer、subject 和过期时间均拒绝；
- Token secret 和密码不会进入日志。

### 阶段四：REST、Middleware 和 bootstrap
交付：

- 登录 REST Handler；
- JWT Middleware；
- 公开和受保护路由接线；
- 基于 Principal 的 Authorizer 和 CurrentAuthorProvider 适配器；
- bootstrap 配置、Repository、identity application、JWT 和 REST 依赖装配；
- 现有 CurrentAuthorProvider 与认证身份连接。

验收：

- 登录接口无需 Token；
- 管理接口无 Token 或无效 Token 返回 401；
- 有效 Token 可进入管理业务路径；
- 有效 Token 能提供当前作者身份；
- 公开读取仍无需 Token；
- 启动、readiness 和关闭顺序不改变。

### 阶段五：OpenAPI、契约和端到端验证

交付：

- OpenAPI 源契约；
- 生成 bindings；
- 内嵌 OpenAPI 文档；
- contract、REST、integration 和 E2E 测试；
- 受影响架构文档和开发指南中的当前事实更新。

验收：

```text
POST /api/v1/auth/login                 -> 200
管理接口无 Authorization                 -> 401
管理接口使用无效 JWT                     -> 401
管理接口使用 admin JWT                   -> 业务处理
公开读取无 Authorization                 -> 正常返回
```

## 10. 风险与回退

| 风险 | 处理 |
| --- | --- |
| 默认密码弱 | 明确属于初始固定账号；数据库只保存 bcrypt hash；后续增加改密或部署前密码替换能力 |
| JWT secret 泄露 | 不写入日志；通过配置替换 secret；secret 变化使旧 Token 失效 |
| 禁用用户仍能使用旧 Token | Middleware 每次验证后查询当前活动用户 |
| 重复 migration 覆盖密码 | 默认账号使用 `ON CONFLICT DO NOTHING` |
| OpenAPI 生成物不同步 | 以源契约生成，并运行两个生成物检查任务 |
| 认证接线影响公开读取 | 只在受保护路由挂载 Middleware，并执行公开读取 E2E |
| 迁移失败 | 修复 migration 后重新执行；应用在 migration 版本不是 4 或处于 dirty 状态时不启动 |

回退方式：

- 代码回退不能跳过已应用的 migration；
- 如需回退 schema，使用对应 migration down，并确认该操作会删除 `users` 表及其数据；
- 不自动删除或重建现有 content 数据；
- 生产环境回退前保留数据库备份和 migration 状态记录。
