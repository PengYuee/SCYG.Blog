## 2. 当前项目边界

`backend/` 是仓库唯一的 Go module，运行单体 REST/HTTP API；启用 Agent 集成后，同一进程提供内部 BlogContent gRPC。当前业务模块为：

- 身份认证与用户登录；
- 文章查询、创建、局部更新、发布、归档和删除；
- 文章类型与标签查询、维护；
- 文章正文图片上传、引用、媒体读取和清理；
- PostgreSQL 持久化；
- 本地文件系统图片 Blob 存储；
- `/live`、`/ready` 和自托管 API 文档。

Blog 已接入八个 JWT HTTP/SSE 路由、AgentControlService 客户端与八 RPC BlogContentService listener。Agent 仍是 Run、owner、状态、事件和结果的权威；Blog 不保存 Agent Run 表、事件或结果，仅保存文章写入的 `article_operations` 成功幂等账本。

## 4. 本地环境和运行

### 4.1 工具版本

- Go `1.26.8`；
- Task `v3.49.1`；
- PostgreSQL `17.5`；
- 固定工具版本见 `backend/Taskfile.yml`。

### 4.2 配置

1. 复制 `backend/config.example.yaml` 为本地未跟踪的 `backend/config.local.yaml`。
2. 填写数据库 DSN 和本地图片存储目录。
3. QA 使用独立的 `backend/config.qa.example.yaml`，不要把 QA DSN 写入运行时配置。
4. 不提交包含真实密码的本地配置。

Agent 默认关闭；启用时配置 `agent.enabled`、`target`、`blog_content_listen`、`unary_timeout`、`sse_idle_timeout`、`grpc_shutdown_timeout`。默认 target 为 `127.0.0.1:9090`，BlogContent listener 为 `127.0.0.1:50051`。

### 4.3 启动

从 `backend/` 执行：

```text
CONFIG=config.local.yaml task migrate:up
go run ./cmd/api -config config.local.yaml
```

API 默认配置文件为 `config.local.yaml`。应用启动时检查数据库连接、迁移版本和依赖装配；运行时不会自动执行 migration，也不使用 `AutoMigrate`。

健康端点：

```text
GET /live
GET /ready
```

Agent 离线不是 Blog 启动或 readiness 的前置条件；启用集成时，BlogContent listener 绑定失败会使启动失败。标准 `grpc.health.v1.Health` 随应用启动完成变为 SERVING，关闭开始即撤回健康状态。关闭顺序为 HTTP/SSE 排空、使用独立 `agent.grpc_shutdown_timeout` 预算排空 gRPC、停止 worker、关闭 Agent client、数据库和遥测。

### 4.4 Docker Compose

```text
task compose:smoke
task compose:down
```

`compose:smoke` 完成后必须清理 Compose 资源；完整 QA 容器流程使用 `task qa:container`。

上述 Task 是后端自身容器门禁；Blog↔Agent 联合配置位于根 `compose.yaml`，使用根目录构建上下文。Blog 启动以自身数据库及初始化就绪为前提，不依赖 Agent 在线；内部 gRPC 端口不发布到宿主机。初始化流程见[开发指南](../docs/services/backend/guides/backend-development.md#6-配置和-qa-数据库)。

## 6. 架构约束

- 使用手动构造函数注入；不使用 Wire、Fx、Dig、service locator 或可变全局依赖容器。
- 业务 feature 不导入 Gin、生成的 OpenAPI 或 platform/database；Repository 才可使用 GORM 和数据库适配器。
- `article`、`taxonomy`、`image`、`operation` 各自拥有业务规则和持久化边界；feature 不导入兄弟 feature。
- `content/application` 只负责具名跨 feature 工作流和事务边界，不直接写 SQL、访问 Record 或 Repository。
- 持久化使用版本化 SQL migration，不使用 `AutoMigrate`。
- 生命周期、乐观并发控制和 claim 写入必须使用显式列集合、条件 `WHERE` 和 `RowsAffected` 检查。
- 列表分页由数据库执行；排序只能使用白名单并包含稳定二级排序键。
- 外部 Blob 清理使用短事务 claim，事务外执行文件操作，再用精确 token 完成或释放。
- 新的公开 REST 接口必须先更新 `backend/api/openapi.yaml`，再重新生成 bindings 和内嵌文档。

详细约束以 [`backend/AGENTS.md`](../backend/AGENTS.md) 和现行架构文档为准。

## 7. 当前认证和权限

HTTP 登录入口为 `/api/v1/auth/login`，成功后获得 Bearer JWT。REST middleware 将已验证 principal 写入 request context；受保护路由要求有效 principal，公开文章、分类、标签和媒体读取路径按 OpenAPI 策略开放。

当前 content 授权以 Blog 现有认证和资源规则为准。不要在新 feature 中自行复制 JWT 解析、用户上下文或授权判定；应通过现有认证边界和消费方窄接口接入。

## 8. Agent API 交接重点

当前接入入口以 OpenAPI、共享 Proto 和实际适配器为准：

| Blog JWT 路由 | 行为 |
| --- | --- |
| `POST /api/v1/ai/search` | 固定 search capability 创建 Run |
| `POST /api/v1/ai/write` | 固定 write capability 创建 Run |
| `POST /api/v1/ai/polish` | 固定 polish capability 创建 Run |
| `POST /api/v1/ai/chat` | 固定 chat capability 创建 Run |
| `GET /api/v1/runs/{runId}` | 查询 Run |
| `GET /api/v1/runs/{runId}/events` | SSE 订阅 |
| `POST /api/v1/runs/{runId}/resume` | 恢复 Run |
| `POST /api/v1/runs/{runId}/cancel` | 取消 Run |

八个入口均使用 Blog Bearer JWT；Blog 将已验证 `user_id` 传给 Agent，由 Agent 校验 Run owner。创建和恢复要求 UUIDv4 `Idempotency-Key`；SSE 将不透明 `Last-Event-ID` 传给 Agent，并原样转发 Agent 已编码 frame。`agent.enabled=false` 时整组路由不注册并返回 404。

共享 Proto 位于 `contracts/proto/scyg/agent/v1/` 与 `contracts/proto/scyg/blog/v1/`，不是未来 `api/proto/` 空壳。AgentControlService 为 CreateRun、GetRun、StreamRunEvents、ResumeRun、CancelRun 五 RPC。BlogContentService 为 SearchArticles、GetArticle、ListTags、ListArticleTypes、CreateArticle、UpdateArticle、PublishArticle、ArchiveArticle 八 RPC，使用现有管理查询、分页、排序白名单、状态机、乐观版本和图片引用规则，不限于公开文章投影。

内部 gRPC 使用可信内部网络，不使用 service JWT；BlogContent 仍校验 `user_id` 对应活动账号并应用现有业务授权。不得将内部端口公开，也不得据此扩大 Agent 生产 Tool 写权限。

四个写 RPC 要求全局 UUIDv4 `operation_id`。`content/application/ArticleOperations` 在同一 PostgreSQL 事务内仲裁键、写文章及图片引用、提交成功账本；成功时起算 24 小时，失败回滚不占键。有效成功键重放返回绑定文章的当前管理投影，而不重新执行写入；重放仍经过当前用户授权。Create/Update 的 Blob 预备读取在事务外执行，预备错误只在排除成功重放后用于新写入。过期成功记录由现有清理 worker 有界清理；Blog 不以 Redis 代替最终幂等。

## 9. 本轮验证交接

本轮已运行干净生成、发行包/镜像构建、真实 PostgreSQL 幂等与回滚、HTTP/SSE、关闭预算、根 Compose 及真实 Provider 业务场景；质量门禁与代码审查按实际日志留存于本地任务材料，不用历史结果代替当前版本。合同基线使用已批准的真实 base/head SHA，保留 Buf 的实际诊断；当前验收结果由任务记录维护。共享合同变化应同步生成 Go/Python bindings、OpenAPI、迁移和受影响测试；本文不替代具体执行记录。

## 10. 已知风险和检查入口

- 当前后端文档已迁移到根 `docs/services/backend/`；修改旧 `backend/docs/` 路径不会更新正式文档。
- 本轮已切换共享 AgentControl/BlogContent Proto 与双向接入，不应重新引入旧协议或兼容入口。
- 根 `compose.yaml` 已提供 Blog↔Agent 集成定义；它不同于 `backend/compose.yaml` 的后端容器门禁，执行时必须选择正确文件与构建上下文。
- 生成物不应手工编辑；修改 Proto 或 OpenAPI 后应从源合同重新生成。
- 当前仓库可能同时存在 frontend、agent 和计划目录的其他工作区变更；交接时只提交已明确授权的文件，避免使用全仓库 `git add .` 混入无关改动。

交接说明的使用标准：新接手者可以从本文定位当前双向接入、复制配置、启动 Blog，并区分已验证的源码行为、合同验收结果与尚未部署的状态。
