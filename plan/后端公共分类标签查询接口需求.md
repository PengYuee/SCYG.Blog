# 公共分类与标签发现接口后端需求

## 1. 目的与边界

本文面向后端开发者，定义公共首页“分类”和“标签”发现模块所需的 REST 接口、响应字段、统计口径、分页排序和公共/管理职责边界。

前端本阶段先使用 mock 分页数据开发，不等待后端接口上线。mock 按本文目标契约建模；后端完成后，前端只替换真实 API 适配器和响应解析，不改变页面分页交互。

本文是接口需求，不是后端实现计划。REST 路径、Schema 和错误响应的最终权威位置仍为 `backend/api/openapi.yaml`；生成 bindings 和内嵌 API 文档必须由 OpenAPI 源契约生成，不能手工修改。

## 2. 已确认的业务规则

### 2.1 公共可见文章

`article_count` 只统计同时满足以下条件的文章：

- `status = 2`，已发布；
- `is_deleted = false`，未删除。

草稿、已归档和已软删除文章均不计入公共数量。

分类或标签只有在 `article_count > 0` 时才属于公共发现列表。没有公开文章的分类、标签不能出现在公共首页的分类块或标签块中。

### 2.2 排序

公共分类和标签列表固定按以下顺序返回：

```sql
ORDER BY article_count DESC, id ASC
```

文章数量相同时必须使用 `id ASC` 作为稳定次序。公共客户端不需要、也不应通过 `sort` 参数改变该发现顺序。

### 2.3 分页

前端使用两种首屏大小：

- 分类：`page_size=10`；
- 标签：`page_size=20`。

“更多分类”和“更多标签”每次只请求下一页。后端必须返回准确的 `PageInfo`，使客户端能够判断是否还有下一页。分页必须发生在公开文章过滤和 `article_count > 0` 过滤之后。

页面大小仍受通用分页约束限制，最大值为 `100`。后端不需要为首页首屏大小创建专用接口。

## 3. 公共接口与管理接口

当前 `/api/v1/article-types` 和 `/api/v1/tags` 同时承载读取与写入。需要按文章接口已有的职责边界拆分：公共路径只读，所有 taxonomy 管理写入和作者工作区读取进入 `/manage`。

### 3.1 公共只读路径

```http
GET /api/v1/article-types
GET /api/v1/article-types/{article_type_id}

GET /api/v1/tags
GET /api/v1/tags/{tag_id}
```

公共路径不得再声明或执行以下方法：

```http
POST
PATCH
DELETE
```

公共 GET 不需要认证。列表和详情只返回公共资源模型，不暴露管理端版本、审计时间或菜单排序字段。

### 3.2 管理端路径

```http
GET    /api/v1/manage/article-types
POST   /api/v1/manage/article-types
GET    /api/v1/manage/article-types/{article_type_id}
PATCH  /api/v1/manage/article-types/{article_type_id}
DELETE /api/v1/manage/article-types/{article_type_id}

GET    /api/v1/manage/tags
POST   /api/v1/manage/tags
GET    /api/v1/manage/tags/{tag_id}
PATCH  /api/v1/manage/tags/{tag_id}
DELETE /api/v1/manage/tags/{tag_id}
```

管理端所有方法均保留现有授权、版本和错误语义：

- 需要授权的请求返回 `403`；
- PATCH、DELETE 要求强 `If-Match`；
- 缺失 `If-Match` 返回 `428`；
- 版本不匹配返回 `412`；
- 名称冲突返回 `409`；
- 成功写入返回新的强 `ETag`；
- 创建返回 `201`、`Location` 和初始强 `ETag`；
- 管理资源的 `Location` 使用 `/api/v1/manage/...` 路径。

管理端列表和详情必须保留文章数为 `0` 的未删除分类、标签，保证作者工作区能够管理尚未被公开文章使用的字典项。

## 4. OpenAPI 操作建议

为避免公共和管理操作在生成代码中职责混淆，建议使用唯一且显式的 `operationId`：

| 方法 | 路径 | operationId |
| --- | --- | --- |
| GET | `/api/v1/article-types` | `listPublicArticleTypes` |
| GET | `/api/v1/article-types/{article_type_id}` | `getPublicArticleType` |
| GET | `/api/v1/tags` | `listPublicTags` |
| GET | `/api/v1/tags/{tag_id}` | `getPublicTag` |
| GET | `/api/v1/manage/article-types` | `listManageArticleTypes` |
| POST | `/api/v1/manage/article-types` | `createManageArticleType` |
| GET | `/api/v1/manage/article-types/{article_type_id}` | `getManageArticleType` |
| PATCH | `/api/v1/manage/article-types/{article_type_id}` | `patchManageArticleType` |
| DELETE | `/api/v1/manage/article-types/{article_type_id}` | `deleteManageArticleType` |
| GET | `/api/v1/manage/tags` | `listManageTags` |
| POST | `/api/v1/manage/tags` | `createManageTag` |
| GET | `/api/v1/manage/tags/{tag_id}` | `getManageTag` |
| PATCH | `/api/v1/manage/tags/{tag_id}` | `patchManageTag` |
| DELETE | `/api/v1/manage/tags/{tag_id}` | `deleteManageTag` |

如果保留现有公共 operationId，也必须保证生成后的公共和管理方法、Handler、授权入口不会混用；显式命名优先。

## 5. 公共响应 Schema

### 5.1 公共分类资源

新增 `PublicArticleType`：

```yaml
PublicArticleType:
  type: object
  additionalProperties: false
  required: [id, name, image, article_count]
  properties:
    id:
      $ref: '#/components/schemas/PositiveID'
    name:
      type: string
      minLength: 1
      maxLength: 60
    image:
      type: string
      maxLength: 512
      nullable: true
    article_count:
      type: integer
      format: int64
      minimum: 1
```

`image` 保留公共文章卡片和文章详情使用的分类图片能力。`meun`、`version`、`created_at`、`updated_at` 不属于公共发现资源，不应出现在该 Schema 中。

### 5.2 公共标签资源

新增 `PublicTag`：

```yaml
PublicTag:
  type: object
  additionalProperties: false
  required: [id, name, article_count]
  properties:
    id:
      $ref: '#/components/schemas/PositiveID'
    name:
      type: string
      minLength: 1
      maxLength: 60
    article_count:
      type: integer
      format: int64
      minimum: 1
```

### 5.3 公共分页包络

新增：

```yaml
PublicArticleTypeList:
  type: object
  additionalProperties: false
  required: [items, page]
  properties:
    items:
      type: array
      items:
        $ref: '#/components/schemas/PublicArticleType'
    page:
      $ref: '#/components/schemas/PageInfo'

PublicTagList:
  type: object
  additionalProperties: false
  required: [items, page]
  properties:
    items:
      type: array
      items:
        $ref: '#/components/schemas/PublicTag'
    page:
      $ref: '#/components/schemas/PageInfo'
```

### 5.4 管理资源

管理端可以继续使用当前完整的 `ArticleType`、`Tag` 和对应列表 Schema，或者将其显式重命名为 `ManageArticleType`、`ManageTag`。无论采用哪种命名，管理响应必须保留当前写作台所需的：

- 分类：`id`、`name`、`image`、`meun`、`version`、`created_at`、`updated_at`；
- 标签：`id`、`name`、`version`、`created_at`、`updated_at`。

管理资源不要求增加 `article_count`。如果实现层共享查询投影，也不能让公共响应意外暴露管理字段。

## 6. 公共列表请求参数

公共列表至少支持：

```text
page       从 1 开始，默认 1，最小值 1
page_size  默认 20，范围 1 至 100
q          可选名称关键词，沿用现有搜索语义
```

公共列表不需要开放当前 taxonomy 的 `sort` 参数。服务端固定按 `article_count DESC, id ASC` 返回结果。

当传入 `q` 时：

1. 先按分类或标签名称过滤；
2. 统计满足公开文章条件的文章数量；
3. 删除 `article_count = 0` 的结果；
4. 按固定排序排序；
5. 计算 `total_items`、`total_pages` 并分页。

`PageInfo.total_items` 必须是过滤后的公共分类或标签数量，而不是未删除 taxonomy 总量。没有结果时：

```json
"page": {
  "number": 1,
  "size": 10,
  "total_items": 0,
  "total_pages": 0
}
```

## 7. 统计查询语义

### 7.1 分类数量

分类数量等价于：

```sql
COUNT(articles.id)
```

关联条件：

```sql
articles.article_type_id = article_types.id
AND articles.status = 2
AND articles.is_deleted = false
```

分类本身还必须满足：

```sql
article_types.is_deleted = false
```

只返回聚合结果大于 `0` 的分类。

### 7.2 标签数量

标签数量等价于：

```sql
COUNT(DISTINCT articles.id)
```

关联条件：

```sql
article_tags.tag_id = tags.id
AND articles.id = article_tags.article_id
AND articles.status = 2
AND articles.is_deleted = false
```

标签本身还必须满足：

```sql
tags.is_deleted = false
```

只返回聚合结果大于 `0` 的标签。`COUNT(DISTINCT ...)` 用于明确防止关联行重复导致数量膨胀。

### 7.3 查询与分页顺序

实现必须保持以下逻辑顺序：

```text
过滤未删除 taxonomy
→ 关联已发布且未删除文章
→ 聚合 article_count
→ 排除 article_count = 0
→ 应用名称关键词
→ 按 article_count DESC、id ASC 排序
→ 计算总数
→ LIMIT/OFFSET 分页
```

实际 SQL 可以使用聚合子查询或 CTE，但不得通过逐条 taxonomy 查询文章数量，避免 N+1 查询。

不新增 `article_count` 持久化字段，不引入计数缓存或异步最终一致计数。数量以查询时的公开文章状态为准。

## 8. 文章与分类摘要兼容要求

首页移除按分类分组后，最新文章卡片仍需要显示分类名称和图片。公共文章列表和详情响应因此需要提供分类摘要，避免前端为了渲染文章卡片再请求完整分类字典。

公共 `Article` 资源保留现有 `article_type_id`，并增加：

```yaml
article_type:
  type: object
  additionalProperties: false
  required: [id, name, image]
  properties:
    id:
      $ref: '#/components/schemas/PositiveID'
    name:
      type: string
      minLength: 1
      maxLength: 60
    image:
      type: string
      maxLength: 512
      nullable: true
```

`article_type.id` 必须与 `article_type_id` 一致。该摘要只用于公共文章卡片和详情展示，不替代文章筛选字段；不需要在摘要中增加 `article_count`、`version`、`meun` 或审计时间。

管理端文章响应是否携带该摘要不属于本次公共首页需求；如继续复用同一 `Article` Schema，必须明确该字段对管理端同样可用，且不能因此改变管理端文章写入语义。

## 9. 详情接口语义

公共首页只依赖列表接口；公共详情接口不是本次分页交互的必要依赖。为保持公共/管理边界清晰，公共详情应返回对应的 `PublicArticleType` 或 `PublicTag`，而管理详情返回完整管理资源。

公共详情至少应过滤软删除资源。若实现同时要求公共详情与公共列表完全一致，则没有公开文章的资源返回 `404`；该行为必须在 OpenAPI 描述和 REST 测试中明确。无论采用哪种详情策略，公共详情不得返回版本、管理时间和菜单排序字段。

## 9. 性能与数据库要求

本需求不要求新增计数字段或修改现有表结构。查询应复用现有 `articles`、`article_types`、`tags`、`article_tags` 表及索引。

实现后应检查公开统计查询的执行计划。若真实数据量下需要补充索引，优先考虑与公开条件和关联键匹配的索引，例如：

```sql
CREATE INDEX ...
ON articles (article_type_id)
WHERE status = 2 AND is_deleted = false;
```

标签统计至少应能利用 `article_tags(tag_id)` 和文章主键连接。是否添加迁移由实际 `EXPLAIN` 结果决定，不以增加冗余计数字段解决。

## 10. 错误与授权边界

公共 GET：

- 参数非法返回现有 `400` RFC 9457 Problem；
- 数据库或未处理故障返回现有 `500` Problem；
- 不要求登录，不返回 `403`。

管理 GET/POST/PATCH/DELETE：

- 遵循现有 taxonomy 授权策略；
- Handler 在进入 Repository 或 UnitOfWork 前完成授权；
- 继续使用现有 `403`、`404`、`409`、`412`、`428` 和 `500` 映射；
- 不把数据库密码、API key 或其他配置值拼接进错误和普通日志。

## 11. 验收场景

### 11.1 公共统计正确性

使用真实 PostgreSQL integration fixture 覆盖：

1. 一个分类含两篇已发布未删除文章，返回 `article_count=2`；
2. 只有草稿的分类不返回；
3. 只有归档文章的分类不返回；
4. 只有软删除文章的分类不返回；
5. 软删除分类不返回；
6. 标签只关联一篇公开文章但存在多条无效关联场景时，数量仍按公开文章去重；
7. 软删除标签不返回；
8. 同数量项目按 `id ASC`；
9. `total_items` 和 `total_pages` 基于过滤后的结果。

### 11.2 分页

验证：

- 分类请求 `page_size=10` 时只返回一页；
- 标签请求 `page_size=20` 时只返回一页；
- 后续 page 返回正确连续结果；
- `total_pages=0` 的空结果符合 `PageInfo`；
- 越界页返回空 `items` 和准确总分页信息；
- 同一请求不出现重复项目。

### 11.3 路由职责

验证：

- 公共 GET 不需要授权；
- 公共路径不再执行 taxonomy 创建、修改、删除；
- 管理路径的 GET、POST、PATCH、DELETE 使用 `/api/v1/manage/...`；
- 管理写入仍验证授权、`If-Match`、`ETag`、`Location` 和冲突状态；
- 管理列表仍能返回文章数为 `0` 的未删除分类和标签。

### 11.4 契约同步

至少同步：

- `backend/api/openapi.yaml`；
- `internal/generated/openapi/` 生成 bindings；
- `internal/transport/rest/apidocs/assets/openapi.yaml`；
- REST Handler 和窄接口；
- `internal/contracttest/policy_test.go`、Schema 测试和相关 operation 测试；
- taxonomy unit/integration 测试；
- E2E 中现有 taxonomy 写入 URL。

按照后端开发指南，接口变更至少执行：

```powershell
task api:generate
task api:docs:sync
task qa:contract
```

涉及真实 PostgreSQL 查询和迁移时，还必须执行对应 integration 验证。

## 12. 兼容与交付边界

这是职责边界调整，不保留公共路径的 POST、PATCH、DELETE 兼容别名。前端作者运行时后续必须将 taxonomy 请求切换到 `/api/v1/manage/...`；当前前端分类与标签发现页面先使用 mock，不阻塞后端接口实现。

本需求不改变：

- `/api/v1/articles` 的公开文章筛选参数和响应；
- `/api/v1/manage/articles` 的文章管理接口；
- 文章状态值和软删除语义；
- `article_type_id`、`tag_id` 的文章筛选业务含义；
- 分类和标签删除时的活动文章引用约束。

本需求也不要求持久化文章数量、增加计数维护任务或修改文章写入事务。文章发布、归档、软删除和恢复相关状态变化只需在下一次公共查询时反映到统计结果。
