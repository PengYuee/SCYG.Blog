# 首页分类与标签发现模块前端实施计划

## 1. 目标与结论

在公共首页侧栏增加可分页展开的分类和标签发现模块，帮助访客按主题进入文章筛选页。

首页侧栏顺序固定为：

```text
个人信息
推荐文章
分类
标签
```

本次前端先使用本地 mock 分页数据，不等待后端接口完成。mock 的调用契约按照目标分页响应建模；后端就绪后只替换 API 绑定和响应适配，不改动组件交互与分页状态机。

首页主内容区只保留“最新文章”，展示最多 6 篇；删除现有按分类分组的文章区块。最新文章卡片继续保留现有分类名称和图片展示，但改由公开文章响应中的分类摘要提供，不为卡片额外加载全部分类分页。文章归档页本轮不做视觉重构，只同步 `articleTypeId` 查询键，确保首页分类链接可用。

## 3. 范围

### 3.1 本次交付

1. 建立公共 taxonomy 发现模块的前端分页模型和状态机。
2. 增加可分页展开的分类列表。
3. 修改标签云，展示文章数量并支持分页展开。
4. 首页接入分类和标签发现模块。
5. 删除首页按分类展示文章的主内容区块，只保留最多 6 篇最新文章。
6. 分类和标签链接使用 `articleTypeId`、`tagId` 进入文章筛选页。
7. 在前端请求层预留公共读取与作者管理写入的适配器边界；作者写入路径统一改为 `manage` 路径。
8. 将最新文章卡片的分类名称和图片切换为公开文章分类摘要，不因侧栏分页加载全部分类。
9. 为首页 mock、状态转换、分页加载、错误重试和路由参数增加有行为价值的测试。
10. 使用 Playwright 对 mock 数据下的首页实际交互进行验收。

### 3.2 明确不做

- 不修改后端代码、OpenAPI 或数据库；后端接口调整需求单独交付，不纳入本实施计划。
- 不在本计划中实现真实公共 taxonomy HTTP 适配器；只定义可替换的前端契约并使用 mock。
- 不重做文章归档页的筛选 UI、布局或分页策略；只同步 `articleTypeId` 查询键。
- 不在页面中使用滚动容器承载分类或标签溢出内容。
- 不增加无限滚动、自动预取、离线缓存或跨页面共享 taxonomy 缓存。
- 不改变文章卡片已有的可见字段和视觉信息；只调整分类摘要的数据来源。
- 不修改文章编辑内容、推荐文章算法或文章卡片以外的文章字段。
- 不保留公共路径上的作者写入兼容别名。

## 4. 前端数据模型与 mock 契约

### 4.1 公共发现项

在 `frontend/src/types/taxonomy.ts` 增加面向公共发现模块的内部模型，不复用带版本和管理字段的作者资源：

```ts
export type PublicTaxonomyItem = {
  readonly id: number
  readonly name: string
  readonly articleCount: number
}
```

分类和标签在发现模块中都使用该最小字段集合。分类图片、版本、菜单顺序和审计时间不属于本次侧栏需求。

分页请求在前端内部采用零基 `pageIndex`，便于与现有文章流状态机保持一致；外部 HTTP 适配器将其转换为后端的一基页码。

```ts
export type PublicTaxonomyPageRequest = {
  readonly pageIndex: number
  readonly pageSize: number
}

export interface PublicTaxonomyApi {
  listArticleTypes(request: PublicTaxonomyPageRequest): Promise<PageResult<PublicTaxonomyItem>>
  listTags(request: PublicTaxonomyPageRequest): Promise<PageResult<PublicTaxonomyItem>>
}
```

`PageResult` 复用 `frontend/src/types/api.ts` 的分页结果模型。响应顺序由服务端或 mock 保证，页面不再次按名称排序；mock 按文章数降序、同数量按稳定 ID 顺序生成数据。

### 4.2 最新文章分类摘要

首页移除按分类分组后，最新文章卡片仍需要显示分类名称和图片。因此公共文章列表/详情进入前端领域模型时必须提供分类摘要，不能依赖侧栏分页列表反查：

```ts
export type PublicArticleTypeSummary = {
  readonly id: number
  readonly name: string
  readonly imageUrl: string | null
}
```

`ArticleDetail` 或其公共列表摘要模型增加：

```ts
readonly articleType: PublicArticleTypeSummary
```

前端 mock 文章数据同步提供该摘要；真实 API 适配器从后端文章响应的分类摘要字段映射它。分类 ID 仍保留为 `articleTypeId`，摘要只负责展示，不能替代文章筛选字段。

### 4.3 mock 数据

新增 `frontend/src/mocks/public-taxonomy.ts`，提供 `createMockPublicTaxonomyApi()`：

 - 分类有效数据至少超过 10 项；
 - 标签有效数据至少超过 20 项；
 - 数据中包含文章数为 `0` 的原始条目，但 mock API 在分页前过滤掉它们，模拟公共接口只返回有公开文章的项目；
 - 至少包含文章数相同的项目，用于验证稳定顺序；
 - 每次调用严格按照 `pageIndex`、`pageSize` 返回一页，不自动拉取后续页；
 - 返回的 `totalItems`、`totalPages` 与过滤后的有效项目一致；
 - 未知页码返回空页或稳定的边界结果，不制造重复项目。

mock 不放入组件内部，不通过 `setTimeout` 制造不稳定延迟。需要验证 loading 状态的测试通过可控 Promise 注入测试 API。


## 5. 分页状态与交互规则

新增 `frontend/src/stores/public-taxonomy-discovery.ts`，创建与 UI 无关的公共发现状态机。

### 5.1 单个资源流状态

分类和标签各自维护以下状态：

- 已加载项目；
- 已成功加载的最后页码；
- 总页数；
- 是否正在加载下一页；
- 最近一次加载错误；
- 是否存在下一页。

分类和标签首屏请求并行发起，且错误彼此隔离：一个资源流失败时，另一个资源流仍正常显示；失败块提供自己的重试入口。页面只有在两个首屏请求都仍未结束时显示对应的加载状态，不用一个失败结果清空另一个已经成功的列表。

### 5.2 “更多”加载

- 分类首屏请求页面大小为 `10`。
- 标签首屏请求页面大小为 `20`。
- 每点击一次“更多”，只请求对应资源流的下一页。
- 请求中只禁用对应资源流的“更多”按钮，已加载项目保持可见。
- 成功后按响应顺序追加，并按 ID 去重，不能重复显示已有项目。
- 仍有下一页时保留按钮；全部加载完后隐藏按钮。
- 下一页失败时保留当前列表，显示局部错误和可再次点击的重试按钮；不回退已经成功加载的页。
- 页面不设置固定高度，不使用 `overflow` 滚动容器，追加内容自然展开。
- `articleCount <= 0` 的项目在进入组件前过滤；正常 mock 和未来真实适配器都应已经完成服务端过滤。

- `frontend/src/router/query.ts` 的类型、Schema、解析和序列化全部改为 `articleTypeId`；

前端请求层按职责拆分适配器：

- 公共适配器只保留公共 GET 能力；
- 管理适配器负责作者 taxonomy 的 list/create/update/delete；
- `frontend/src/services/author-runtime.ts` 改为使用管理适配器；
- `frontend/src/request/api-services.ts` 暴露职责明确的服务字段；
- `frontend/src/request/api/article-type.ts`、`tag.ts` 拆分公共读取与管理写入的路径常量和映射；
- 所有作者写入请求改用 `/api/v1/manage/...`；
- 删除公共路径上的 POST/PATCH/DELETE 旧调用和未使用别名；
- 首页发现模块当前使用 mock，不通过公共 HTTP 列表请求绕过分页状态机。

作者页面的版本、`If-Match`、冲突和删除语义保持现有实现，不在本功能中重新设计。

## 10. 实施顺序

### 阶段一：内部模型与 mock 状态机

输入：公共发现项模型、固定首屏大小和分页规则。

交付：`PublicTaxonomyItem`、mock 分页 API、公共发现状态机。

验收：分类首屏最多 10 项、标签首屏最多 20 项；下一页每次只发一页请求；零文章项目不进入结果；失败重试不会丢失已加载项目。

### 阶段二：分类与标签组件

输入：阶段一的状态流和分页操作。

交付：分类列表、带数量标签胶囊、“更多”按钮及局部错误状态。

验收：分类显示名称和数量；标签保持胶囊形式；超过上限后显示“更多”；加载后全部自然展开，无滚动条；链接参数正确。

### 阶段三：首页内容收敛

输入：阶段二组件。

交付：首页侧栏顺序调整、首页分类文章分区删除、最新文章固定最多 6 篇。

验收：推荐文章下方依次出现分类和标签；主内容只保留最新文章；空文章流不影响侧栏展示。

### 阶段四：查询键和服务边界

输入：已有公共路由和作者 runtime。

交付：`articleTypeId` 统一、作者 taxonomy 管理请求切换到 `/manage`、公共读写适配器职责分离。

验收：首页链接可导航到正确筛选查询；作者现有版本化写入行为不变；代码中不再存在公共 taxonomy 写入调用。

### 阶段五：验证与清理

输入：完整 mock 页面和测试夹具。

## 11. 风险与回滚

| 风险 | 处理 |
| --- | --- |
| mock 分页与后端实际分页不一致 | mock 严格使用统一 `PageResult`，保留 page size、total items、total pages 语义；真实适配器只替换数据源 |
| 点击“更多”重复请求或重复渲染 | 状态机以 loading 锁和 ID 去重保证单流串行追加，并用组件测试覆盖 |
| 某一页失败导致已加载内容消失 | 分页错误只保留在对应资源流，已成功项目不可回滚 |
| 分类链接仍使用旧查询键 | 路由 Schema、序列化、页面消费和测试同一阶段切换，禁止保留 `categoryId` 别名 |
| 作者写入仍误走公共路径 | 管理适配器独立命名，API adapter 单测断言完整 URL 和方法 |
| 首页内容高度增加 | 不设固定高度或滚动条；追加内容自然撑开页面，沿用现有布局响应式规则 |

本次没有数据库写入和不可逆前端状态迁移。回滚只需恢复前端构建产物或撤回 mock 发现模块绑定；不涉及后端数据回滚。
