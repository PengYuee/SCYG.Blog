# 分类名称修改功能实施计划

## 1. 目标与结论

为作者工作区增加“修改分类名称”能力，两个入口保持一致：

- 写作台分类下拉框：在现有删除图标旁增加修改图标。
- “分类与标签”管理页：在分类列表项的删除按钮旁增加修改按钮。

本次只修改分类名称，不开放分类图片和菜单排序编辑。文章保存的 `article_type_id` 不变，因此分类改名不会触发文章迁移。

用户可见文案使用“修改分类”“分类名称”，不使用 `slug` 等接口术语。

## 2. 当前事实

| 事实 | 当前来源 |

| 更新请求要求 `If-Match` | OpenAPI `If-Match` 参数；当前适配器按资源版本发送强实体标签 |

## 3. 范围

### 3.1 本次交付

1. 在作者分类仓储契约中增加版本化分类更新方法。
2. 在真实作者运行时连接 `articleType.update`。
3. 在 Fake 作者仓储中实现分类改名，保留版本递增行为。
4. 在写作台分类下拉框增加修改图标和修改事件。
5. 在分类管理页增加修改按钮和修改弹框。
6. 在写作台增加修改分类弹框及请求协调逻辑。
7. 对成功、校验失败、名称重复、版本冲突、目标已删除和普通失败进行处理。
8. 增加单元、组件和必要的 E2E 夹具验证。

### 3.2 明确不做

- 不修改后端 OpenAPI 或后端业务逻辑。
- 不编辑分类图片 `image`。
- 不编辑菜单排序 `meun`。
- 不批量修改文章的 `article_type_id`。
- 不增加新的通用弹框框架。
- 不改变分类删除语义。
- 不增加复杂的离线队列、自动重试或冲突合并。

## 4. 目标接口与领域契约

### 4.1 作者仓储新增方法

在 `AuthorTaxonomyRepository` 增加：

```ts
updateArticleType: (
  request: ArticleTypeUpdateRequest,
) => Promise<AuthorArticleType>
```

请求结构复用现有领域类型：

```ts
{
  id: number
  version: number
  changes: { name?: string }
}
```

本次页面只传递 `changes.name`。

### 4.2 真实 API 映射

`createAuthorRuntime` 中新增：

```ts
updateArticleType: services.articleType.update
```

底层适配器保持现有契约：

```http
PATCH /api/v1/article-types/{id}
If-Match: "{version}"
Content-Type: application/json
```

请求体：

```json
{
  "name": "新的分类名称"
}
```

响应继续通过 `articleTypeSchema` 解析，再映射为带版本的 `AuthorArticleType`。

## 5. 交互设计

### 5.1 写作台分类下拉框

分类操作列由单列调整为两个并列图标：

```text
分类名称                 修改   删除
```

新增事件：

```ts
request-update-article-type: [articleType: AuthorArticleType]
```

按钮要求：

- 修改图标位于删除图标左侧。
- `aria-label` 使用 `修改分类“{name}”`。
- 删除按钮现有语义保持不变。
- 分类下拉框打开时点击修改不能触发分类选择。
- 父级协调期间两个图标均禁用。

### 5.2 修改弹框

弹框字段：

- 标题：`修改分类`
- 输入标签：`分类名称`
- 初始值：目标分类当前名称
- 取消：关闭弹框，不发请求
- 保存：提交去除首尾空白后的名称

保存按钮在以下情况禁用：

- 名称为空或全为空格；
- 名称超过 60 个字符；
- 请求进行中；
- 输入值与原名称相同。

修改失败时不清空输入、不关闭弹框，允许原地重试。

### 5.3 分类管理页

分类列表项增加修改按钮，使用与写作台相同的弹框语义和仓储方法。标签列表本次不增加修改入口，避免扩大需求范围；标签修改 API 已存在，但不属于本次分类功能。

## 6. 状态与失败处理

### 成功

1. 通过共享 mutation guard。
2. 调用 `updateArticleType({ id, version, changes: { name } })`。
3. 使用响应中的完整分类资源替换本地目标。
4. 关闭弹框。
5. 保持当前文章的 `articleTypeId` 不变。
6. 提示“分类已修改”。

### `409 Conflict`

表示名称重复或业务冲突：

- 保留弹框和用户输入；
- 提示“分类名称已存在”；
- 不刷新或覆盖用户输入；
- 允许修改名称后重试。

### `412 Precondition Failed`

表示版本已过期：

1. 重新读取分类列表。
2. 若目标仍存在，用服务端最新版本和名称替换目标。
3. 将最新名称填回弹框。
4. 提示“分类已被其他操作修改，请确认最新名称后再保存”。
5. 要求用户再次点击保存。

不得使用旧版本自动重试，避免覆盖并发修改。

### 目标已删除

刷新后找不到目标分类时：

- 关闭弹框；
- 从本地列表移除目标；
- 若当前文章选中该分类，将 `articleTypeId` 清零；
- 提示“该分类已不存在，当前选择已同步”。

### `403`、`404`、`428` 或其他错误

- 弹框保留；
- 输入内容保留；
- 释放请求锁；
- 按现有作者页面错误归一化规则显示可重试提示；
- 不对后端错误细节做页面层拼接。

### 阶段一：契约接线

输入：现有 `ArticleTypeUpdateRequest`、API `update` 适配器和作者仓储。

交付：真实 runtime 与 Fake runtime 都实现 `updateArticleType`。

验收：类型检查通过；Fake 修改后返回新名称和递增版本；API 请求包含正确路径、请求体和 `If-Match`。

### 阶段二：写作台入口与弹框

输入：阶段一的仓储方法。

交付：下拉框修改图标、事件、弹框、成功和失败状态。

验收：修改图标不触发选择；成功后当前文章分类 ID 不变；失败可重试；并发版本冲突不会静默覆盖。

### 阶段三：分类管理页入口

输入：阶段一的仓储方法和阶段二的交互规则。

交付：管理页修改按钮和同语义弹框。

验收：管理页与写作台使用相同请求契约和错误结果；分类列表最终显示服务端返回名称和版本。

## 9. 风险、回滚与监控点

| 风险 | 处理 |
| --- | --- |
| 分类改名覆盖并发修改 | 必须携带当前版本；`412` 刷新并要求重新确认 |
| 改名后当前文章显示异常 | 文章只保存分类 ID；更新后保留选中 ID并替换分类资源 |
| 修改按钮误触发选择 | 操作按钮使用 `@click.stop`，并覆盖组件测试 |
| 请求失败后用户输入丢失 | 弹框状态与请求状态分离，失败不清空表单 |
| 两个入口行为不一致 | 共用仓储方法、错误规则和响应资源收敛原则 |
| 生产作者能力边界被绕过 | 继续复用现有生产路由门禁和 mutation guard |

本功能没有不可逆数据迁移。回滚只需恢复前端构建产物；后端分类名称已成功修改的记录不会自动回滚，若需要恢复名称必须通过正常修改接口重新提交。

## 11. 待确认事项

当前按以下决策编写计划：

- 修改范围仅限分类名称。
- 两个作者入口同时支持修改。
- 标签修改不纳入本次需求。
